# Регресс File Bridge: пять последовательных музыкальных задач

Это отдельный модельный регресс, а не набор заранее написанных партитур. Сценарий: [scenario.json](../scripts/file-bridge-regression/scenario.json). Композитор получает по одному короткому пользовательскому сообщению; исходные ноты, критерии приёмки и исходный код ему не передаются.

## Роли и границы

- **Sol low — разработчик и приёмщик.** Разрабатывает проверки, читает результаты, принимает или отклоняет предложение через настоящий HALO bridge. Не сочиняет, не исправляет JSON за Luna, не пишет в requests, контекст или responses. Запись контекста и ответов выполняет отдельный логический актор HALO receiver. Это разграничение кода теста, а не отдельная Windows ACL для учётной записи разработчика.
- **Luna low — внешний композитор.** Запускается как `gpt-6-luna` с `model_reasoning_effort=low`, без истории этого чата, проектных инструкций, shell, веба, плагинов и делегирования. Ей предоставлены только `list/read/write/wait` для одной тестовой папки. Пути проверяются адаптером; чтение исходников и запись состояния/ответов запрещены. Проверки вне файлового интерфейса отмечают провал, а не игнорируются.
- **HALO — получатель.** Использует production `src/file-bridge.js`, `src/agent.js` и валидацию проекта. Реальные файлы на диске доступны через совместимые с File System Access дескрипторы. Сервер инструментов общается по локальному IPC; ни HTTP API управления музыкой, ни новый backend HALO не добавляются.

Каждый запуск создаёт **новую** папку `artifacts/file-bridge-regression/<timestamp>/shared`. Все пять задач одного запуска используют именно её и одну сессию Luna. Существующую папку receiver создавать/переподключать не позволяет: пользовательская музыка не затрагивается. Перезапуск всего теста создаёт другой независимый прогон; результаты разных прогонов не объединяются.

## Задания и приёмка

| Шаг | Короткое задание | Что проверяется по реальным событиям |
| --- | --- | --- |
| 1 | Новогодний мажорный луп на 8 тактов 4/4 | Авторские ноты, мелодия хотя бы в 6 тактах, минимум 3 её высоты, звучащее pitched-сопровождение. Тематика и качество требуют прослушивания. |
| 2 | Сделать из этой фразы законченную композицию | Не менее 3 музыкально разных фраз и 3 секций; фразы различаются нотами/ритмами, а не ID, тембром или mute. Сохраняется мотив первого лупа, как минимум две разные фразы связаны мелодическим мотивом; вступление и финал могут обходиться без полной мелодии. Форма свободная. |
| 3 | Всю композицию в 3/4, ре минор, вдвое медленнее | Точное деление BPM на 2, все фразы в 3/4 и D minor, события внутри 12 шагов на такт; переработанные ноты, связанный контур мелодии, сохранённые ID/порядок/повторы частей. Отдельно проверяются фактические высоты, а не только key. |
| 4 | Совершенно новая оригинальная пиратская композиция | Минимум 3 разные фразы; другой мотив и как минимум 2 сменённых тембра. Минор и активная перкуссия — измеримые признаки энергичности, не доказательство пиратского звучания. |
| 5 | Только выключить ударные во всей композиции | Меняется исключительно on на false у фактически непитчевых ударных/шумовых партий. Все ноты, тембры, настройки, мелодические голоса и структура должны остаться побитово равными нормализованному предыдущему проекту. |

Мотив сравнивается через тройки последовательных мелодических интервалов; для сохранения узнаваемости при переработке — через направления движения. Различие новой темы: нет идентичной последовательности высот/стартов; Jaccard сходство уникальных интервальных троек меньше 0,6. Обычные совпавшие обороты допустимы. Эти эвристики не доказывают художественную ценность, узнаваемость на слух или отсутствие заимствований.

Проверка высот шага 3 допускает натуральный, гармонический и мелодический D minor: до-диез и си допустимы, фа-диез — нет. Это проверка словаря высот и метаданных, а не доказательство тонального центра; намеренный хроматизм требует отдельного музыкального рассмотрения. Систематическая мажорная терция не должна пройти как «минор» лишь из-за key. Метрики считаются с учётом noteTranspose, key offset и акустического ограничения регистров движка.

## Порядок и ошибки

Перед каждой новой задачей обязателен настоящий probe → ready с одним новым ID. Затем тот же ID используется для музыки; актуальность проверяет HALO. Агент получает только нормализованный STATE.score, без внутреннего project. Для шага 5 требуется mode:patch. Перед каждой записью требуется чтение live state; руководство достаточно прочитать один раз в сохраняющейся сессии. Новый пользовательский запрос получает новый ID. Root-файл читается обратно; принимается только ответ с этим ID. Чтение старого applied для сверки не завершает новый запрос.

Luna прекращает работу после pending_approval или терминального ответа **текущего** запроса. Только после завершения её хода Sol оценивает preview и нажимает эквивалент Apply/Reject через bridge. Применение подтверждается настоящим receipt и изменением ревизии; следующий промпт сообщает об одобрении только после фактического применения.

HALO-ошибки возвращаются как есть. Адаптер не чинит и не нормализует партитуры. Максимум 3 записи одного файла за ход, 3 чтения одной версии receipt, 80 файловых вызовов и 240 секунд на ход. Любая попытка превышения/выхода за папку проваливает приёмку, даже если защита её заблокировала. Отсутствующий receipt допускается как штатная ситуация; бесконечного ожидания нет. Лимиты — инструментальная защита, а журнал показывает, соблюдала ли их сама модель.

При провале зависимого шага цепочка не объявляется успешной. После отклонения неудачного шага 3 можно выполнить независимое новое задание 4; шаг 5 зависит от принятого шага 4. Провал 1/2/4 останавливает прогон. Никакие неудачные результаты не подменяются ручной партитурой.

## Запуск

Без обращений к модели:

```powershell
node --test tests/file-bridge*.test.cjs
```

Строгий live-прогон (использует авторизацию установленного Codex CLI и расходует лимиты Luna):

```powershell
$env:HALO_CODEX_BIN = (Get-Command codex).Source
node scripts/file-bridge-regression/run.cjs
```

Для диагностического покрытия всех пяти задач, даже если модель допустила содержательную или дисциплинарную ошибку:

```powershell
node scripts/file-bridge-regression/run.cjs --diagnostic
```

В этом режиме приёмщик может применить валидный HALO preview **только для продолжения теста**. `accepted` остаётся false, появляется `appliedForContinuation: true`, и общий результат остаётся fail. Повреждённые/неподтверждённые запросы и нарушения границ доступа продолжение не разрешают. Этот режим не заменяет строгую приёмку и не скрывает дефекты за зелёным статусом.

Результаты: `report.json`, промпты и JSONL модели для каждого шага, `file-access.jsonl`, исходные отправленные файлы, receipts и снимки before/proposed/after. SHA-256 критериев сохраняется в отчёте. `pass` означает автоматическую структурную/протокольную приёмку; `musicalReview: NOT_PERFORMED` отдельно показывает отсутствие прослушивания. Не записывайте «качественный новогодний/пиратский трек принят» на основании этого флага.

Для повторной оценки сохранённых снимков после исправления ошибки **самого теста**:

```powershell
node scripts/file-bridge-regression/recheck.cjs artifacts/file-bridge-regression/<timestamp>
```

Она создаёт отдельный recheck.json, сохраняя первоначальный report.json. Музыка и shared-папка не меняются. Такое исправление критерия надо объяснять в отчёте; оно не должно превращаться в подбор порогов ради зелёного результата.

Конфигурация изоляции использует [официальные параметры Codex](https://learn.chatgpt.com/docs/config-file/config-reference): отключение shell, project docs и поинструментальные разрешения MCP. Разрешены только четыре собственных ограниченных инструмента; глобальные пользовательские настройки не меняются.

## Область доказательства

Это проверка реального поведения отдельной Luna low и настоящего File Bridge на файловой системе. Она не проверяет Qwen 9B, браузерный выбор папки, сохранение нативного permission grant, устройства, реальное воспроизведение или художественную приёмку на слух. Для завершения музыкальной приёмки надо прослушать принятые проекты в HALO и отдельно записать оценку тематики, связности, лупа, развития и звучания после mute.
